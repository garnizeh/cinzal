# D04 — What does Riot do to a sector's trail entries, and how does it avoid becoming a fog channel?

**Status:** decided
**Blocks:** M1 — Rules core
**Decided:** 2026-08-08
**Issue:** [#42](https://github.com/garnizeh/cinzal/issues/42)

## The question

GDD §14.3 gives Riot one sentence: *"Every trail entry generated in this sector this round is randomized. Names, events, all of it."* Nothing else in either document mentions it. It is the only card in the deck with a fog dimension — everything else in §14.2/§14.3 is a public, global effect. What does "randomized" mean precisely, and how does it avoid manufacturing disclosures about players the effect never touched?

## Why it is open

The trail log (GDD §7.3) is the deduction game's primary data structure, and it is a mix of two genuinely different kinds of entry: five types are **global announcements of real game state** (delivery, post staked, lease expired, Loitering, loose crate held — RFC §9.1's Distribution column), and three are **sight-gated traces that only exist in the fog** (cargo taken, confrontation, item purchased — the same column, same three rows: 1, 7, 8). A fourth, fresh tracks, is sight-gated too but carries no name and sits outside RFC §9.1's eleven-row table entirely, because that table only enumerates writers of *named* position information.

"Randomized... names, events, all of it" reads as touching all eight GDD §7.3 event types with no distinction between the two kinds. Left that way, it is ambiguous on every axis that matters:

- **Permute existing entries, or regenerate new ones from the vocabulary?** Regeneration can invent a name for a player who was never in the sector, which is a disclosure *about that player*, generated by a card they had no part in — worse than any leak the fog boundary is built to prevent, because it isn't even true.
- **Can it touch the five global types?** A delivery entry is tied to a real contract completion and a real payment; a post staking is tied to a real occupied node. Randomizing *those* doesn't distort the trail, it contradicts an already-broadcast fact about the match.
- **Does the affected player get lied to about their own round?** They read the log of the node they personally ended on. If Riot silently replaces what they see there with something they didn't do, that isn't fog — it's a bug wearing a card's clothes.
- **[D3](D03-rng-consumption-table.md) needs an index cost.** Its own table reserved Riot's row with one hard constraint already fixed: *"exactly one index per randomized trail entry — not per node, not per player."* Any method this decision picks has to produce that count, not `n − 1`, not something conditional on the sector's size.

## Options

**A — Permute existing sight-gated entries among the sector's nodes.** Contents (event type, whether it's named, and the name) travel with the entry; only which node it's attached to moves. No name is ever spoken that wasn't already in the sector this round. Cost: in a quiet round with zero or one eligible entry, the card is a no-op — a real cost, but an honest one, not a reason to reach for fabrication instead.

**B — Regenerate entries from the vocabulary, names included.** The most literal reading of "names... all of it." Cost: it can name a player who was never in the sector, which needs its own row in RFC §9.1's authorised-writer table and a rule stopping it from naming someone below their real Infamy's name gate — and it hands the negative fog suite (RFC §9.3, §16.3) a permanent, card-shaped exception to "a name may not appear at a node its owner never visited," which is the exact property every other rule in the game is written to preserve.

**C — Suppress: write nothing in the sector this round.** Trivially fog-safe and deterministic, but it is `Rain` (GDD §14.2) with a smaller radius, which is the strongest argument for cutting the card rather than keeping a redundant one.

## Decision

**A. Riot permutes; it never invents, and it never touches a global entry.**

**Scope — which entries are eligible.** Exactly the trail entries generated this round at nodes inside the flagged Unstable sector whose distribution is **sight-gated**, per RFC §9.1's own Distribution column: cargo taken, confrontation, item purchased — plus fresh tracks, which is sight-gated too but outside that table because it never names anyone. The five **global** types (delivery, post staked, lease expired, Loitering, loose crate held) are untouched, categorically, not as a matter of degree: they are broadcasts of real game state that other systems and other players already hold as fact by the time Phase 7 runs, and reassigning their node would contradict something already true rather than merely obscure it.

**Mechanism.** Build the canonical list of eligible entries, sorted by `(origin NodeID, entry-type declaration order per GDD §7.3's table, acting SeatID)` — the same no-map-iteration discipline RFC §6.4 mandates everywhere else. Copy their origin nodes into a second slice of the same length, `n`. Run Torn Map's exact mandated shuffle (RFC §6.4) over that slice — partial Fisher-Yates, `purpose = "incident.riot"`, loop `i := 0` to `n−1`, drawing `rng.Next("incident.riot", n−i)` each iteration, including the last:

```go
entries := sortedEligibleEntries(sectorID, round)   // len n; see Scope
targets := originNodesOf(entries)                    // same n, a copy
for i := range targets {
    j := i + rng.Next("incident.riot", len(targets)-i)
    targets[i], targets[j] = targets[j], targets[i]
}
for i, e := range entries {
    e.Node = targets[i]   // event type, name, and whether it's named: unchanged
}
```

This is a **closed permutation of the entries that actually occurred** — the target pool is the multiset of real origin nodes, never the sector's full node list. A node with zero real activity this round can never receive a Riot-manufactured entry; every node's post-shuffle log is always some other node's *real* entry, never a fabricated one. That is what keeps this Option A and not Option B in different clothes: widening the target pool to "any node in the sector" would let the card assert that something happened at a node where nothing did, which is exactly the kind of false claim the naming argument already rules out — it would just be making it about a location instead of a person.

**Cost, matching [D3](D03-rng-consumption-table.md)'s reservation exactly.** The loop above draws once per `i` from `0` to `n−1` inclusive — `n` draws, not `n−1` — because it is Torn Map's *selection* shape (`min(k, n)` at `k = n`), not the deck-order *shuffle* shape RFC §6.4 costs at `n−1` elsewhere. No special-casing is needed to hit D3's "one index per entry, not per node, not per player": it falls out of reusing the existing mandated selection algorithm at the right value of `k`. `n = 0` costs nothing, matching RFC §6.4's lazy-draw rule (§6.4) for a quiet round with no eligible entries in the sector.

**Naming.** No entry acquires a name it didn't already carry, and no name gate is re-evaluated. Cargo taken stays named only if the real actor's real Infamy was ≥ 3 at the time; item purchased stays named only at Infamy ≥ 6; confrontation stays named for both real parties, always; fresh tracks stays unnamed, always. The permutation moves *where* the entry is read, never *what* it says or *who* it's about.

**What the acting player sees.** A player whose own entry was relocated this round is told, privately, that one of their traces in this sector was moved by Riot — not which node it moved to, and not what now sits at the node they actually stood on. Telling them *that much* discloses nothing they don't already know (they know what they did and where); telling them less would mean the game silently disagreeing with their own lived round, which GDD §7.1's fog model never does to a player about their own actions elsewhere. Telling them the destination, or the identity of whichever real entry got shuffled onto their true node, would leak a second player's business through a channel neither player consented to by playing normally.

**What everyone else sees.** Nothing new. The sector's Unstable flag and the fact that Riot is the incident resolving there are already public from the Headline (GDD §14.3, §14.1) before Phase 7 runs. A reader with sight into that sector this round already knows, from the public card name alone, that the log they're about to read has been shuffled — the shuffle itself discloses no additional fact about any specific node.

**RFC §9.1: no new row, and no footnote either.** The permutation runs inside resolution (Phase 7, `writeTrail`/the incident handler — [#71](https://github.com/garnizeh/cinzal/issues/71), [#73](https://github.com/garnizeh/cinzal/issues/73)), strictly before `Resolve` returns for the round. By the time `Project` ([#75](https://github.com/garnizeh/cinzal/issues/75)) reads `MatchState`, the permuted assignment *is* the trail entry — there is nothing left for the fog boundary to know about Riot specifically. Rows 1, 7 and 8 of RFC §9.1's table behave exactly as documented, reading whatever `MatchState` already holds; `writeAnchors` needs zero new cases. This is the cleaner answer than the caveat the issue anticipated: Riot is entirely a `Resolve`-time transformation of the record, not a `Project`-time one, so the eleven-writer table is unaffected as a *table* — its outputs are just sometimes, honestly, attached to the wrong node for one round in one sector, which is the card working as designed rather than the projection leaking.

## Reasoning

**Splitting the trail table into "global" and "sight-gated" is not a new distinction invented for this decision — it is already the Distribution column of RFC §9.1's own table**, and treating it as load-bearing here is the same move RFC §9.1 already makes for every other row: "treating a confrontation as global is a leak; treating a delivery as sight-gated breaks the anchor system." Riot's scope rule is that sentence generalized to a card instead of to `Project`.

**A closed permutation over real origin nodes is strictly narrower than "shuffle among the sector's nodes," and that narrowness is the entire argument for why this is Option A and not Option B.** Any target pool wider than the entries that actually fired lets the card manufacture a location fact that isn't true — a node with a real Riot-attached entry despite nothing having happened there. That is fabrication about a place instead of a person, but it is fabrication of the same kind Option A exists to rule out, and the narrower reading closes it for free.

**The `n` vs. `n − 1` question resolves by recognizing which of RFC §6.4's two already-mandated shapes this is.** Selecting `k` of `n` candidates (Dragnet's 2 Borders, Torn Map's 4 hidden nodes, [D3](D03-rng-consumption-table.md)'s seven near-identical rows) costs `k`, including at `k = n`. Ordering an already-fixed set into a sequence (the event/incident deck's final shuffle) costs `n − 1`, because the last element's position is forced once every other has one. Riot is the first shape — it is *assigning* `n` entries their `n` new node labels — not the second, and D3's "exactly one per entry" requirement is simply naming the cost that shape already has. No new rule was needed; the existing two-shape taxonomy in RFC §6.4/§6.5 already had a slot for this.

**Withholding the destination from the acting player, while still telling them something moved, threads a needle GDD §7.1 already drew.** `SelfState` is exact — a player is never lied to about their own balance, cargo, or contracts. A silently corrupted read of their own node's log would be the trail-log equivalent of that same lie. But GDD §7.1's fog model is otherwise strictly about *other* players' facts staying private from *you* — so the fix that respects both halves at once is "confirm the fact that's already yours (something of mine moved), withhold the fact that isn't (where, and whose real entry landed on my node)."

**Multiplicity of same-type, same-node entries (e.g., two different players' fresh tracks crossing the same node the same round) is a `writeTrail` construction question, not this decision's.** Whether the trail log deduplicates anonymous entries per node or keeps one per passerby changes `n`, not the method — the algorithm above operates on however many entries `writeTrail` actually constructs. [#71](https://github.com/garnizeh/cinzal/issues/71) owns that choice; this decision is agnostic to it by design, the same way [D3](D03-rng-consumption-table.md) stayed agnostic to card-specific mechanics it didn't need to settle.

## Consequences

- **GDD §14.3 gains an explanatory passage under the HAZARDS table**, stating the permute-not-regenerate rule, the global/sight-gated split, and the two disclosure rules (acting player told, not where; everyone else told nothing new) — this PR.
- **[D3](D03-rng-consumption-table.md)'s Riot row is completed in this same pull request**, replacing "reserved — count fixed by D4" with the concrete method and the exact-`n` cost, and its closing paragraph and Consequences bullet are updated to reflect that the row is no longer open — the same move [D8](D08-sector-size-constraint.md) made when it unblocked D3's Sinkhole and Scaffolding rows.
- **A real, independent bug found while confirming the Distribution column: RFC §9.1's own prose is stale against its current table.** The paragraph beginning "Rows 1–5 and 7–9 reach every player unconditionally. Row 6 is a trail entry: it names both parties..." and the one beginning "Rows 4 and 5 announce a node, not a player" both predate r8's insertion of the cargo-taken row at position 1, which shifted every row after it by one — the table itself is correct (confirmed against GDD §7.3 row for row, and against issue [#75](https://github.com/garnizeh/cinzal/issues/75)'s own independently-restated table, which already uses the current numbers), but the prose two paragraphs below it was never updated. Fixed in this PR: "unconditionally" now reads rows 2–6 and 9–11; "sight-gated" now names rows 1, 7 and 8; "announce a node, not a player" now names rows 5 and 6. This is the table this decision depends on for the global/sight-gated split, so leaving the stale prose in place risked a second implementer trusting the wrong sentence the way the original one apparently did.
- **RFC §6.4's table is not edited in this PR.** Per D3's own precedent (and D6/D7/D8/D9's before it), the row lands with whoever implements the RNG accounting ([#56](https://github.com/garnizeh/cinzal/issues/56)) and sector incidents ([#73](https://github.com/garnizeh/cinzal/issues/73)), using D3 (now completed) as the source of truth.
- **[#73](https://github.com/garnizeh/cinzal/issues/73) is unblocked** — it already cited "Riot (per #42)" in its own body without a definition to point to.
- **[#73](https://github.com/garnizeh/cinzal/issues/73)'s implementer should note Riot's targeting differs from every other incident's.** The rest of §14.3 hits "every player whose route ended inside" the sector; Riot's scope is entry-based, not player-based — it can move a fresh-tracks entry left by someone who only passed through, not just those who ended there. Worth stating explicitly so the generic "ending in the sector" filter isn't reflexively applied to this one card too.
- **No RFC §9.1 edit lands anywhere, for either implementer.** Confirmed above: the permutation is fully resolved before `Project` runs, so [#75](https://github.com/garnizeh/cinzal/issues/75) needs no new case and no caveat.
- **`SeatArchive` (RFC §9.2) stores whatever the player actually received, post-permutation, permanently.** A Riot round contributes at most one mis-located data point to that player's own Heat Map history — bounded, self-consistent with what they were actually shown that round, and small against the 15-round sample the rate is computed over. No new mechanism needed; this is a natural consequence of the archive recording observations rather than ground truth.
- Reversible at low cost while `internal/rules`'s incident handling is unwritten; expensive after, for the same golden-replay reason every entry in this log carries — a fixed test seed bakes in whichever permutation Riot produced for it.
