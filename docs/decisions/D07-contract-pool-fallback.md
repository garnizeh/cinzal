# D07 — What happens when the contract pool runs short or empty mid-match?

**Status:** decided
**Blocks:** M1 — Rules core
**Decided:** 2026-08-08
**Issue:** [#45](https://github.com/garnizeh/cinzal/issues/45)

## The question

GDD §8.1's rule of generation only offers a contract whose **origin** is a Warehouse the player already **Know**s, at a §8.3 tier's distance band from a **destination** Border. §6.1 constraint 7 guarantees that pool is non-empty **at setup, for the opening offer, only**. Nothing guarantees it later — a player who explores little Knows few Warehouses, a Legend needs distance 6+ from one of them, and `Bridge Down` destroys an edge permanently and can push a pair out of every band it was in. What does the generator do when fewer than three valid contracts exist, and what does it do when none do?

## Why it is open

Silence here is not a rules gap that shows up as an odd match — it is a crash or an infinite retry loop inside the generator, mid-match, on a seed nobody can reproduce without the log. §8.1's own history is exactly this failure mode once already: v1.8 required both endpoints Known, which made the *opening* offer mathematically impossible in every match (three lines of proof, now recorded in §8.1 itself), and v1.9 fixed it by revealing the destination instead. That fix guarantees the pool at round 1. It says nothing about round 9, and the pool is a function of a fog state that only ever grows for a given player but is checked against a fixed set of Borders and a graph that can *shrink* — `Bridge Down` removes an edge permanently, and `Sinkhole` makes a node impassable for 3 rounds, both changing what "distance" means for every contract check that follows (GDD §9.1a item 0: distances are computed against the **currently navigable graph**, never the static setup graph).

This also isn't isolated. It ties to [D6](https://github.com/garnizeh/cinzal/issues/44) (open): D6's leading option guarantees a contract at the player's highest eligible tier, and that guarantee is unsatisfiable exactly when this decision's fallback would otherwise trigger — D6 cannot be written correctly without an answer here first, whichever way D6 itself resolves. It also feeds [D3](D03-rng-consumption-table.md): RFC §6.4 already carries a `contract.offer` row, fixed at "3 per offering seat," which stops being accurate the moment the offer can come up short. And it feeds task [#63](https://github.com/garnizeh/cinzal/issues/63) (`internal/rules`: contracts), which is blocked on this issue by name and already writes its acceptance criteria against a fallback and a truncated index count that didn't exist in writing until now.

## Options

**A — Offer fewer than three.** Honest, trivially deterministic, and the UI already has to handle "decline all" — one fewer card on the table is not a new UI state. Cost: the offer draw's index count becomes variable, which D3's table (fixed at "3 per offering seat") needs to absorb.

**B — Relax the distance band.** Keeps three cards on the table by widening a tier's distance range until a pair fits. Cost: it isn't just a balance smell, it's structurally pointless. §8.3's four bands — 3–4, 4–6, 5–8, 6+ — already union to *every* distance from 3 upward with no gap between them (4 and 6 are each covered twice, on purpose or not, but nothing above 3 is left uncovered). Widening a band can never make a previously-invalid pair valid, because there is no distance left for a wider band to reach that some existing band doesn't already cover — the only thing widening a band can do is **reclassify an already-valid pair under a cheaper tier's payout**, which is the dial GDD §16 says to touch last, edited by a fallback path instead of a playtesting pass.

**C — Relax the Known-origin rule**, offering a Rumoured or unknown Warehouse as origin. Cost: it deletes the exploration incentive §8.1 exists to create ("Exploration keeps its return, too — a wider Known map means more origins available") and hands the player a free map fact they did not earn, which is a bigger version of the exact mistake v1.9's changelog already records fixing once (destinations were briefly "Known" instead of "Rumoured," for the same reason: it hands over a plottable route for nothing).

**D — Drop to a lower tier and fill from there**, never a higher one. Costs the player payout, not the game a rule — a Legend who can't get a Tier IV slot filled gets a cheaper contract instead of an empty slot, which is a worse outcome for them but not a broken one. The obvious objection — "why not also check a *higher* tier if it happens to have room?" — is rejected for the same reason as B: a higher tier pays more for less exploration, and that is a reward for underexploring dressed up as a fallback.

## Decision

**D, chained into A, as a single deterministic cascade. Never B, never C.**

For a slot whose target tier is `t` (assigned by whatever tier-mix rule D6 settles on — this decision is agnostic to that rule; it only fixes what happens when the pool that rule wants to draw from is empty):

1. Try `t`'s own candidate pool: `(origin, destination)` pairs where `origin` is a Warehouse the player Knows, `destination` is any Border, and the shortest path between them **on the currently navigable graph** falls in `t`'s distance band.
2. If empty, try `t − 1`, then `t − 2`, down to Tier I. Never `t + 1` or above — see Reasoning.
3. If Tier I's pool is also empty, the slot is dropped. The offer is delivered with however many slots the cascade actually filled, `0` to `3`.

This is bounded and terminating by construction: at most 3 slots × 4 tier attempts = 12 pool lookups, each a lookup and (on success) a single draw — never a redraw of the same tier, never a "keep trying until three are found" loop. Eligibility never needs a separate check inside the cascade: Infamy thresholds are cumulative (0/3/6/9 for I/II/III/IV), so eligibility for `t` already implies eligibility for every tier below it, and the cascade only ever moves downward.

**The zero-offer case.** If every eligible tier's pool is empty — for a Nobody, that's just Tier I; for a Legend, all four — no contracts are offered this round. This reuses GDD §8.2's own precedent for the 2-active-contracts case rather than inventing a second mechanism: **the cooldown does not restart, and the offer is held, delivered at the first subsequent Phase 2 where the pool (at whatever size it then supports) is non-empty.** A held-for-full-slots condition and a held-for-empty-pool condition compose — a round waits on both being clear before delivering.

**Disclosure: yes.** The offer surface states why it's short (or absent) rather than staying silent — "fewer contracts than usual" or equivalent, on a short offer; "no offer this round" continuing to show the ordinary cooldown display, on a held one. This discloses nothing the player doesn't already know about their own fog: they can already see how many Warehouses they Know. It's the same judgment call §8.2 already made for the cooldown itself — "always displayed... never a surprise" — extended to the one case that display doesn't currently cover.

**D6 must build on this, not the reverse.** Whatever tier-mix rule D6 settles on (its own recommendation is: guarantee one contract at the player's highest eligible tier, the other two drawn uniformly) is satisfied by handing each of its target tiers through this cascade — the guarantee, if D6 adopts one, is "the slot gets filled at the highest tier the cascade can reach," not "the slot gets filled at exactly the assigned tier or is left empty." D6's own issue already flags this ordering explicitly and this decision settles it in that direction.

## Reasoning

**Widening a band is not just bad practice here, it's a no-op on validity and a live one on payout.** This is worth stating precisely because it's a stronger argument than "don't touch balance in a fallback path": the four distance bands in §8.3 were very likely written to overlap on purpose — a distance-6 pair is valid for II, III, *and* IV simultaneously — specifically so that generation always has a choice of which tier to file a given pair under. That structural fact is exactly what makes cascading downward (Option D) free of the cost Option B pays: the pool problem this decision exists to solve is never "no pair exists at this distance," it's "no Known Warehouse reaches any Border at a distance this tier's band wants." Widening the band doesn't fix that; dropping to a tier whose band the *existing* distance already satisfies does.

**The cascade only moves downward, on purpose, even past a tier with room.** If Tier III's pool is empty but Tier IV's has stock, the cascade still does not reach for IV — doing so is Option B's mistake wearing Option D's clothes, paying Tier IV money for a run the player's own exploration only earned a Tier III shot at. The asymmetry is deliberate: cascading down costs the player, cascading up would pay them, and only the first is an acceptable fallback.

**The zero-offer condition is a statement about reachability, not distance, once the bands are taken as given.** Since the four bands jointly cover every distance from 3 upward with no gap, a Known-Warehouse-to-Border pair fails to land in *any* tier's pool only if it isn't at a valid distance in the first place — which, on the currently navigable graph, means unreachable, not merely far. `Bridge Down` is the mechanism most likely to cause this: it is a single, unique card in the 24-card event pool (per [D3](D03-rng-consumption-table.md)'s own accounting, it resolves at most once a match), but D3's own Reasoning section left open whether the edge it destroys is allowed to be a graph-theoretic bridge — i.e., whether it may disconnect the graph rather than merely shrink it. If it can, and it happens to isolate the only Warehouse(s) a thinly-explored player Knows from every Border, that's the zero-offer state this decision hands to the held-offer path rather than a crash. This decision does not resolve D3's open question — it doesn't need to, because the fallback here is triggered by testing whether the pool is empty, not by knowing in advance why it might be. `Sinkhole` can contribute to the same state in principle, but far more weakly: it clears in 3 rounds, comfortably inside every tier's deadline (4 to 6 rounds), so on its own it is a stall, not a dead end.

**This decision does not need, and does not claim, that "not adjacent" (§6.1 constraint 6) is the same fact as "every delivery costs at least 3 steps," which is the very next sentence in the same constraint.** Non-adjacency alone only forces distance ≥ 2, not ≥ 3; whether the stated 3-step floor holds by construction, or depends on an interaction with the map's other constraints that isn't spelled out, is a question about map generation, not about this decision. The fallback ladder above is correct either way: it acts on whether a tier's pool is empty, and a pair at distance 2 (if the generator can ever produce one) simply doesn't populate any tier's pool, the same as an unreachable one — it needs no special case. Worth a follow-up doc-consistency check against `rules/gen` once it exists, but not a blocker here.

**Reusing §8.2's held-offer mechanism instead of inventing a second one is the same move D9 made reusing §6.2's declaration order for its tie-break** — a fixed, already-stated rule is one fewer arbitrary thing to invent, and a player-facing precedent ("the cooldown does not restart while held, the offer arrives the moment the block clears") that already exists is exactly the shape this gap needed.

## Consequences

- **GDD §8.1 gains the fallback ladder and §8.2 gains the empty-pool hold**, both stated as player-facing rules, with a changelog entry — this PR.
- **RFC §6.4's `contract.offer` row is not edited in this PR.** Per D3's own precedent ("decisions produce a document, not code") and D01/D02's before it, the table edit lands with whoever implements the RNG accounting for `internal/rules` ([#56](https://github.com/garnizeh/cinzal/issues/56)) and the contract subsystem itself ([#63](https://github.com/garnizeh/cinzal/issues/63)), using this document as the source of truth. What that implementer needs to know, stated here so it isn't silently skipped the way D3 flagged its own version of this gap: the row's fixed **3 per offering seat** becomes **`min(3, filled)` per offering seat**, `filled` being however many slots the cascade above actually produces (`0` to `3`); each filled slot costs exactly one draw (a single pick from that slot's resolved tier's pool), never a redraw of an already-checked tier, so the count is variable but still cheap and still bounded — the same `min(k, n)` shape D3 already established for Torn Map and eight of its own ten gaps.
- **[D6](https://github.com/garnizeh/cinzal/issues/44) is unblocked in the one direction that matters**: whatever tier-mix rule it settles on now has a defined answer for what happens when its target tier comes up dry, and its own issue text already anticipated the answer would come from here.
- **[#63](https://github.com/garnizeh/cinzal/issues/63) is unblocked**: its acceptance criteria already reference "#45's fallback" and "#45's short-pool truncation" by name.
- Reversible at low cost while `rules/contracts` is unwritten; expensive after, for the same golden-replay reason every decision in this log carries — a fixed test seed bakes in whatever offer size the fallback produced for it.
