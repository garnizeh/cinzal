# D33 — Which GDD §22 metrics are computable from the Event stream, and what does the rest need?

**Status:** decided
**Blocks:** [#196](https://github.com/garnizeh/cinzal/issues/196) (`internal/rules`: emit the events GDD §22 needs and the stream does not carry), [#197](https://github.com/garnizeh/cinzal/issues/197) (`internal/telemetry`: the per-match metric set, with its denominators), [#199](https://github.com/garnizeh/cinzal/issues/199)/[#200](https://github.com/garnizeh/cinzal/issues/200) (`cmd/simulate`), and through them the exit demonstrations that read those numbers ([#203](https://github.com/garnizeh/cinzal/issues/203), [#204](https://github.com/garnizeh/cinzal/issues/204), [#205](https://github.com/garnizeh/cinzal/issues/205))
**Decided:** 2026-08-17
**Issue:** [#187](https://github.com/garnizeh/cinzal/issues/187)

## The question

RFC §17 states the GDD §22 metric set is *"computed from the event stream."* GDD §22's per-match table has twenty rows (the issue that opened this decision counted twenty-one; recounting the rendered table at `docs/project/cinzal-gdd.md:1562-1581` gives twenty data rows — a small correction worth making once, in writing, rather than carrying an off-by-one into #196/#197). Against those twenty, `game.Event` (`internal/game/event.go`) has 22 kinds and eight fields: `Kind`, `Round`, `Node`, `Seat`, `Target`, `Item`, `Contract`, `Tier`. Most of the twenty rows have no event, or the wrong event, to read.

So: **which of §22's twenty metrics does M2 owe, from what, and what has to change in `internal/rules` to make the rest computable?**

## Why it is open

**The RFC's "one computation, three sinks" only works if the input is the same in all three.** The roadmap's own table states it as a rule: *"One computation, three sinks: `cmd/simulate` CSV, the analytics table, the debug panel. Never three implementations."* `cmd/simulate` and the debug panel both have the final `MatchState` in hand; the web/render path never does, and must never (RFC §3, §5). If the answer to some rows is "read the final state," that is defensible, but it fixes telemetry's position relative to the fog boundary permanently, and it is D34 (#188)'s input.

**Adding events to `rules` is cheap now and expensive after the fixtures exist.** M1's golden replays (#77) assert on the event stream; every new `EventKind` or `Event` field changes those fixtures. `Event` construction consumes no RNG indices (unlike [D32](D32-bot-rng-stream.md)), so this costs fixtures and review, not determinism — but it is one deliberate cost paid once, not N costs paid piecemeal as each sweep discovers a missing number.

**A metric with no denominator silently becomes a different metric.** R1's threshold is *"> 15% of submitted routes"* (GDD §20, §22), with an action attached — soften the confrontation rule. Dividing a truncation count by matches, by player-rounds, or by routes of at least two steps produces three different numbers, and the pipeline would not flag which one it computed. That failure mode is the risk the roadmap already names as P1 (M2 producing numbers that look like answers), which is why this audit is written out row by row rather than answered in the abstract.

## The audit

Classification per row, against the code as it stands today (`internal/rules`, `internal/game`):

| # | GDD §22 metric | Classification | What's missing / where it lives |
|---|---|---|---|
| 1 | Routes cancelled mid-route (R1) | **Needs a new event + order-log access** | Not `EventRouteTruncated` — that fires on Step 0 pre-movement degradation (a destroyed edge), a different mechanic from R1's own framing ("take a confrontation on step one, lose everything after it"). The actual mechanism is `haltMovement` (`confront.go`), called on every confrontation loser, on a tie participant, and on a winner whose own position was corrected — it zeroes `validated[seat].Route` in memory, live, with no event marking that it happened. Needs one new event fired at the halt point (numerator). The denominator — "of submitted routes" — is inherently an order-log fact (`Order.Route`, as declared, before `haltMovement` ever runs), not something a new event should duplicate. |
| 2 | Deliveries per player | **Computable today** | `EventDelivered` carries `Seat`; group and count. |
| 3 | Winner's RP lead over last place | **Needs a final-state read** | RP is not solely a sum of `EventDelivered`'s `Contract`/`Tier`: GDD §10.4 pays **2 RP per live lease at final scoring**, plus **+3 RP for sector majority**, both computed once, at the end, from live `Post` state (`Post.Owner`, `Post.RoundsRemaining` — `state.go:62`). No event exists for either, and none should: they are a fact about the board's state at round 15, not an occurrence during it. |
| 4 | Matches where a player reached Infamy 9 | **Needs a final-state read** | `EventTierLegend` fires for the whole 9–10 band, not the value 9 specifically (`event.go:70-73`), so it cannot distinguish 9 from 10 on its own. Cheaper than a new event fired on the specific crossing (which would need its own fixture cost for a one-off distinction): read the raw `Infamy` value at scoring, the same final-state read row 5 already needs. |
| 5 | Matches where a player stayed at Infamy ≤ 2 to the end | **Needs a final-state read** | No event exists below the Feared tier (Infamy 6) at all — anonymity produces silence by design (GDD §11). Only a final `Infamy` read answers this. |
| 6 | Sector incidents actually hitting a player | **Needs new events** | `incident()` (`incidents.go:166`) dispatches to per-card resolvers; `resolveFlood`, `resolveTorched`, `resolveStreetsBlocked`, `resolveSinkhole`, `resolveLocalInformant`, `resolveDistractedGuard`, and a Turf War loss all mutate `MatchState` directly and return **no event** — only `resolveSnatchJob`, `resolveGuardSweep`, `resolveShakedown`, `resolveInformantRing`, `resolveSpilledLoad`, `resolveOpenDoors` do. Needs a "this seat was actually affected" signal from every currently-silent resolver — distinct from row 12 below, which needs only exposure, not effect. |
| 7 | Live leases at final scoring, per player | **Needs a final-state read** | `Post.RoundsRemaining > 0` grouped by `Post.Owner`, at `Round == cfg.Rounds`. `EventLeaseExpired` tells you when a lease died, never how many are still alive. |
| 8 | Share of map under sight in the final third | **Needs a final-state read — and it's the fog-private kind** | `game.SeatArchive.Sight` (`archive.go:37-47`) already carries exactly this — but it is explicitly **"never crosses to any seat but its own owner"** (RFC §9.2). A cross-player aggregate needs every seat's own archive at once, which no `PlayerView`/`Project()` call ever hands out together. This is not reachable from the fog-safe side of the boundary at all; only a post-match, full-`MatchState`-adjacent read can compute it. |
| 9 | Confrontations won against an Evasive loser | **Needs two small additions, not a new kind** | `decisiveEvents` (`confront.go:509`) already sets `Seat` = winner, `Target` = loser for every decisive `EventConfrontation` — the winner/loser pairing is *already on the event*. What's missing is the loser's declared `Stance`, which lives on the order (`validated[seat].Stance`), not the event: add a `Stance` field to `Event`, populated only for `EventConfrontation`'s `Target`. That alone is not sufficient, though — `tieEvents` (same file) emits the *identical* `EventConfrontation` shape for a tie, and its `Seat`/`Target` pairing is an adjacency chain, not a winner/loser pair. A `Stance` field with no outcome marker lets a tied Evasive `Target` get miscounted as a win. Needs an explicit decisive-vs-tie discriminator alongside `Stance` — cheapest is a boolean (e.g. `Decisive bool`, set by `decisiveEvents` and left false by `tieEvents`), not a second `EventKind`. |
| 10 | Confrontations per match, 4–5 players | **Computable today, with a grouping caveat** | Count distinct `(Round, Node)` pairs among `EventConfrontation` entries, not raw event count: a K-way tie emits K−1 events for one confrontation (`tieEvents`), and a multi-loser decisive result emits one event per loser for one confrontation (`decisiveEvents`) — raw counting overcounts either shape. Player count is `len(MatchState.Players)`, a setup fact, not itself fog-sensitive. |
| 11 | Confrontations per match, 2 players | **Computable today** | Same as row 10. |
| 12 | Players ending a route in a flagged unstable sector | **Needs a new event** | `incidentEligible()` (`incidents.go:96`) already computes exactly this set — every seat whose live `Position` lies in the flagged sector, net of a Circulation Permit discard — but it is scoped to `incident()`'s own resolution and produces no event of its own. Needs one new event fired for every seat in that set, independent of what the incident then does to them (that's row 6). Which sector was flagged is itself reconstructible without a new event, since `s.UnstableSector`'s draw is deterministic from the match seed — but *which seats ended there* is a live-position fact with no event today. |
| 13 | Share of RP swing traceable to [O] cards | **Needs new events on every RP/Cr$-affecting resolution — the most expensive row here** | The card identity for a given round needs no new event: `buildEventDeck`/`buildIncidentDeck` (`cards.go`) are deterministic in the match seed, so "which card was live round N" is re-derivable exactly the way [D32](D32-bot-rng-stream.md)'s `BotRNG` reasoning already established for bot draws. What *is* missing is attribution: most `[O]`-tagged effects (Market Surge, Retainer, Amnesty, New Boss, and the silent incident resolvers in row 6) change `Balance`/`Infamy`/`RP` with no event naming the cause. Answering this cleanly needs either a new event on every such resolution, or a per-round `MatchState` diff cross-referenced against the seed-derived card identity — the latter is a materially heavier ask than any other row here (a full per-round fold, not a final read), because event sourcing keeps no snapshots (RFC §7.1). Recommend scoping this row down for M2's first pass rather than building the general per-round diff machinery to answer it exactly. |
| 14 | Convergence [C] cards that produced a confrontation | **Partially computable today, causation needs more** | Same seed-derivable card identity as row 13. Read loosely — "a confrontation occurred in a round a `[C]` card was live" — this is computable today from `Event.Round` alone. Read strictly — the card's own effect *caused* the confrontation, as opposed to coincidence — needs the same attribution gap as row 13. GDD text ("the convergence tag is decorative" if this stays low) reads compatibly with the loose version; worth a design call before #197, not assumed here. |
| 15 | Attribution queries that ruled out at least one player | **Deferred to M5.5** | A human-facing tool interaction over a UI that does not exist yet (GDD §7.5's Log/attribution tool is M5 scope); not a headless fact at all. |
| 16 | Heat Map opened per player per match | **Deferred to M5** | UI instrumentation — a click count on a feature not yet built. |
| 17 | Rounds flagged as Loitering | **Computable today** | `EventLoitering` fires exactly on the numerator (streak ≥ 2, `trail.go:455-464`). The denominator, "player-rounds," is `len(Players) × cfg.Rounds` — plain arithmetic over setup facts already in hand, not itself an event and not something one is needed for. |
| 18 | Loitering flags triggered by legitimate short-haul play | **No operational definition exists to compute against** | Nothing in the ruleset labels a flag "legitimate" versus "camping" — that is exactly the ambiguity the GDD's own fails-if band names ("the 1-step radius is too wide, or the action exemption too narrow"). This is a design judgment call about *why* a player stayed, which `evaluateLoitering` (`trail.go:439`) structurally cannot distinguish, closer to a human-reviewed sample (M5.5-shaped) than a stream computation — flagging it here rather than pretending a formula exists. |
| 19 | Heat Map entries at low confidence (< 3 observations) | **Needs a final-state read — same fog-private shape as row 8** | `game.NodeStats.ObservedRounds` (`archive.go:75-76`), sourced from the same per-seat, owner-only `SeatArchive`. |
| 20 | Confrontations occurring in the final 3 rounds | **Computable today** | `Event.Round >= cfg.Rounds - 2`, with the same `(Round, Node)` grouping caveat as row 10. |

**Cross-cutting finding: the order log is a hard dependency, independent of how any individual row is answered.** Row 1's denominator ("of submitted routes") is inherently order-log-shaped — inventing a new event whose only job is to restate what the order log already records (a route was submitted) is exactly the "state read wearing an event costume" the roadmap's Option A discussion warns against. Telemetry needs order-log access no matter which of rows 1–20 get new events, which is a real constraint on D34 (#188), not merely a preference.

**Second cross-cutting finding: rows 8 and 19 are not just "state, not events" — they are fog-private state.** `SeatArchive` is deliberately scoped to its own owner and never aggregated across seats anywhere in `internal/rules` today. A telemetry computation needs every seat's archive at once, which structurally cannot come from `Project()`/`PlayerView` — only a full-state read, post-match, reaches it. This is the sharpest version of the "some metrics are genuinely state-shaped" argument the issue opened with.

## Options

**A — Audit all twenty rows now; add every event and field needed for everything headless; read nothing from `MatchState`.**

- For: telemetry stays a leaf over `internal/game`, importable from anywhere, including `web`. Cleanest position relative to the fog boundary.
- Against: rows 3, 7, 8, 19 are genuinely state-shaped — final lease counts, sector-majority RP, and fog-private per-seat archives. Forcing them into events means inventing end-of-match summary events whose only consumer is telemetry, restating facts the state already holds. Row 1's denominator makes the same point even sharper: it is order-log-shaped, not event-shaped, no matter how the event side is designed.

**B — Audit now; events for what is event-shaped (rows 1's numerator, 6, 9, 12, and — with a caveat — 13/14); a final-state read for what is state-shaped (rows 3, 4, 5, 7, 8, 19), plus order-log access for row 1's denominator.**

- For: honest about which is which, and it is what the audit above actually found — most rows split cleanly, only two (13/14) are genuinely expensive.
- Against: telemetry now imports `internal/rules` (for the state reads and the order log), so it can never be imported by `web`/`render`. Needs D34 to place it accordingly, and needs the fog gate to cover the new edge — telemetry reads full `MatchState`, including every seat's private archive, deliberately and by design, which is exactly the kind of access the fog gate exists to keep out of `render`/`web`.

**C — Ship M2 against the subset the current stream already supports (rows 2, 10, 11, 17, 20); defer the rest.**

- For: fastest to a first CSV.
- Against: the subset excludes the lease rate (row 7), R1 (row 1), and R7's Infamy-9 threshold (row 4) — three of the rows the roadmap's own exit-criteria table cites by name. M2 would close on numbers it did not produce for the risks it exists to answer, which is the roadmap's own P1 failure mode.

## Decision

**B.** Split by row, as tabulated above:

- **Rows computable today, unchanged:** 2, 10, 11, 17, 20 (with row 10/11's `(Round, Node)` grouping caveat carried into #197 as a note, not a code change here).
- **Rows needing a final-state read** (`MatchState`, read once at scoring, never through `Project`): 3, 4, 5, 7, 8, 19.
- **Rows needing order-log access:** row 1's denominator, independent of anything else.
- **Rows needing new events, added in [#196](https://github.com/garnizeh/cinzal/issues/196):**
  - Row 1's numerator — one new event fired at `haltMovement`'s confrontation call sites.
  - Row 6 — a "this seat was actually affected" signal from every currently-silent incident resolver (`resolveFlood`, `resolveTorched`, `resolveStreetsBlocked`, `resolveSinkhole`, `resolveLocalInformant`, `resolveDistractedGuard`, Turf War's loss branch).
  - Row 9 — a `Stance` field on `Event`, populated for `EventConfrontation`'s `Target` only, plus a `Decisive bool` (or equivalent) so a tie's identically-shaped `EventConfrontation` can't be miscounted as a win. Two fields, not a new kind.
  - Row 12 — one new event fired for every seat `incidentEligible()` already identifies, independent of row 6's hit signal.
- **Rows 13/14, scoped down for M2's first pass:** ship row 14 against the loose ("confrontation occurred in a `[C]`-card round") reading, using the seed-derivable card identity and no new event. Row 13 is the one metric in this table without a clean answer at either the event or the state-read layer — recommend #197 note it as open pending a design call on whether the loose per-round reading is an acceptable proxy for "traceable to," rather than building general per-round `MatchState` diffing to answer it exactly.
- **Rows 15, 16 — out of scope for M2, UI instrumentation (M5).**
- **Row 18 — out of scope for a stream computation at all; no operational definition exists to compute against.**

## Reasoning

**The audit, not the abstract argument, is what settles A versus B.** Option A's appeal is architectural cleanliness, but four rows (3, 7, 8, 19) are not close calls once read against the actual code: sector-majority RP and lease-count-at-scoring are final-`MatchState` facts with no natural event shape, and `SeatArchive` is fog-private by explicit design (RFC §9.2's own words), never aggregated across seats anywhere today. Inventing events for these would mean an end-of-match summary event whose only reader is telemetry — the "state read wearing an event costume" pattern the roadmap already names as the wrong answer. B is not a compromise reached by splitting the difference; it is what fell out of checking each row against `internal/rules` as it stands.

**Most of the audit turned out cheaper than the issue that opened it feared.** Twelve of twenty rows need either nothing new or a small, well-scoped addition — a field here, one new event there. Only rows 13 and 8/19 carry real cost: 13 because RP/Cr$ attribution has no existing shape to reuse, and 8/19 because they cross the fog boundary by design, not by oversight. Concentrating the decision's cost on the two or three rows that actually carry it, rather than treating all twenty as equally hard, is what makes B's `internal/rules` footprint small — four narrowly-scoped additions, not a sweep.

**Card identity turned out not to need a new event at all**, in either row 13 or 14 — `buildEventDeck`/`buildIncidentDeck`'s determinism in the match seed means "which card was live this round" is a `{seed}`-derivable fact, the identical move [D32](D32-bot-rng-stream.md) already made for bot draws under the same "one computation, three sinks" discipline. What actually costs something in rows 13/14 is attribution (which effect the card's resolution had), not identity — worth separating explicitly, since the issue that opened this decision treated "no event names a card" as the whole problem, when it is only half of it.

**Rejecting A directly:** not because state-shaped facts can't be forced into events — they can, mechanically — but because doing so for rows 3/7/8/19 buys nothing: the resulting events would have exactly one reader (telemetry), would restate facts `MatchState` already holds, and would still leave `SeatArchive`'s owner-only scoping as a design constraint the new events would have to somehow also respect or quietly violate.

**Rejecting C:** the subset it ships is real, but it excludes the lease rate, R1, and R7's Infamy-9 threshold — three of the numbers the roadmap's own exit-criteria table names by row. Closing M2 on that subset is the exact failure the roadmap calls out as risk P1: numbers that look like answers.

## Consequences

- **`internal/telemetry` (or wherever D34 (#188) places it) needs three inputs, not one: `game.Event`, `internal/rules`' final `MatchState` (including per-seat `SeatArchive` for every seat), and the order log — separately, since `MatchState` itself carries none of the order history.** `Resolve` receives orders as its own argument, distinct from the `MatchState` it folds into (`resolve.go`); `haltMovement` (`confront.go:472`) clears routes only on that in-memory, per-round `validated` copy, never on the persisted log a submitted route came from. Row 1's denominator needs that persisted log specifically. RFC §17's "computed from the event stream" needs a correcting footnote in the [#202](https://github.com/garnizeh/cinzal/issues/202) documentation catch-up: computed from the event stream, the final state, and the order log, for the rows this decision found to need each. This decision document is the source for that correction until #202 lands.
- **`internal/rules` gains, in [#196](https://github.com/garnizeh/cinzal/issues/196):** one new `EventKind` for confrontation-caused route halting (row 1), one new `EventKind` (or a shared one) for a silent-incident-resolver hit signal (row 6), a `Stance` field on `Event` (row 9), and one new `EventKind` for sector-incident exposure (row 12) — four additions, not a sweep across all twenty rows.
- **Every addition above changes M1's golden replay fixtures** (#77) — a re-record, not a determinism risk, matching D32's own framing: `Event` construction consumes no RNG indices, so `seq` accounting is untouched; the cost is fixture review, paid once for this batch rather than once per row as #197 discovers each gap independently.
- **Row 13 (RP swing traceable to `[O]` cards) ships without a precise answer in M2's first pass.** #197 should record it as an explicitly open metric rather than a silently approximate one — the GDD threshold exists to catch a real balance problem, and a proxy number that looks precise but isn't is worse than a metric marked "not yet answered."
- **The fog gate's scope needs to explicitly clear telemetry's access to `MatchState`**, the same way it already clears `cmd/simulate` and the debug panel — telemetry reading every seat's private archive is by design here, not a leak, but the CI check that enforces `render`/`web` never importing anything `MatchState`-shaped (RFC §5, §9.1) needs to know telemetry is a fourth sanctioned reader, not a violation to flag.
- **Reversible at moderate cost.** Before #196 lands, this is a documents-only change, reversible by superseding this file. After #196's fixtures are recorded and #197 is built against this classification, moving a row from "final-state read" to "new event" (or the reverse) costs a fixture re-record and a `#197` rewrite for that row's computation — real but bounded, not the whole-match-invalidating cost D32 names for its own reversal.
