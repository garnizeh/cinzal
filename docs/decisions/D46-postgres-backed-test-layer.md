# D46 — How does the Postgres-backed test layer run, and what does it do when there is no database?

**Status:** decided — `integration-list`'s placement relative to `check`'s aggregate is corrected by [D54](D54-integration-tag-fog-gate-and-check-scope.md)
**Blocks:** every M3 exit criterion that exercises real persistence (roadmap §4: fold-from-log equality, the two-processes-one-migration race, `cmd/replay --rebuild` byte-identity, the fold-metrics dashboard, #332) — none of which can be asserted without a database to run against — and all three of M4's concurrency exit criteria (two goroutines producing exactly one resolution, the `deadline_at ± 1ms` boundary against the real Postgres clock, the ten-refold zero-`outbox`-rows regression, roadmap §4)
**Decided:** 2026-08-26
**Issue:** [#309](https://github.com/garnizeh/cinzal/issues/309)

## The question

RFC §16.1 adds two test layers with no existing precedent in this repo: Integration (real Postgres in a container, a full match through the HTTP layer) and Concurrency (two goroutines racing the last order of a round, asserted against a real Postgres clock at `deadline_at ± 1ms`, §8.1). Every test today is pure Go with no external dependency, and `make check` needs nothing but the toolchain (CONTRIBUTING.md, §"Requirements": *"No Node, no frontend build step, and no Docker for the rules engine"*). Three things have to be decided together before the first `_test.go` file for `internal/store` assumes an answer:

1. How does a test get a database — testcontainers-go, a CI service container plus `DATABASE_URL`, or a `docker compose` file the developer runs first?
2. What does a Postgres-backed test do when there is no Postgres — `t.Skip` or `t.Fatal`?
3. Is it inside `make check`, and if not, where does it sit relative to the Makefile's existing reasoned exclusions (`generate-check`, `bench-compare`)?

## Why it is open

**Question 2 is this repository's own fail-closed rule pointed at a new target, and the reflexive Go answer violates it.** CLAUDE.md and CONTRIBUTING both state it in almost identical words: *"a gate that passes when it can't run is worse than no gate."* The idiomatic Go shape for a test needing an external service — `if os.Getenv("DATABASE_URL") == "" { t.Skip(...) }` — is a green `go test ./...` having run zero integration tests, the exact shape this project has already rejected twice: once for the CI gates themselves (`make`'s `require-%` target fails rather than skipping when a tool is missing), once for CodeRabbit reporting success on a review it never ran (`coderabbit-limit-merge-rule` — the standing lesson here is the same one, aimed at a different bot). Left to convention, M3's entire persistence layer becomes untested on any machine where a variable happens to be unset, and the suite still prints `ok`.

The counter-argument is real, not a strawman to wave off: a hard failure on every `go test ./...` means nobody can run the fast inner loop on `internal/rules` — the package edited most, and one that imports nothing (D01) — without first having Docker running. That coupling is exactly backwards, and CONTRIBUTING.md already promises no Docker dependency for the rules engine. The decision needs a shape that keeps both promises rather than trading one for the other.

**Question 1 has a determinism dimension that is easy to miss.** §16.1's Concurrency layer asserts a submission at `deadline_at ± 1ms` lands on the correct side of the boundary *against a real Postgres clock* (§8.1) — meaningless against a database whose clock, timezone, or `now()` semantics differ from production's, and flaky against a container still warming up when the test's first query lands. Whatever supplies the database has to supply **the same one, every time** — a pinned image digest, not the floating `postgres:16` tag — and the mechanism chosen for question 1 has to make that pin trivial to keep, not an extra policy layered on top.

**Question 3 interacts with an existing, already-reasoned decision.** The Makefile keeps `generate-check` and `bench-compare` out of the `check` aggregate today, each with an inline comment stating why; whatever this decision picks for the Postgres-backed layer belongs in that same comment block, following the same discipline — not a fourth ad-hoc carve-out with its own logic.

## Options

### Mechanism (question 1)

- **A CI service container (`services:` in `ci.yml`) + `DATABASE_URL`.** Idiomatic GitHub Actions, but it names the database twice: once as a `services:` block CI understands, once as whatever a contributor's machine is told to run locally to match it. Those two descriptions can drift, and a CI-only failure stops reproducing locally with one command — the exact property CONTRIBUTING.md already calls out as `make check`'s whole value (*"a CI failure reproduces locally with one command"*).
- **A `docker compose` file the developer runs first.** Same two-descriptions problem in reverse: CI would either reuse the compose file (an extra `docker compose up`/health-wait step bolted onto the workflow, duplicating what a service container already does natively) or maintain its own `services:` block anyway, and now there are two files to keep in sync instead of one.
- **testcontainers-go, invoked from inside the Go test binary itself.** One mechanism, one artifact: a pinned image reference as a Go constant, started by the test process itself via the Docker daemon already present on both a contributor's laptop and a GitHub-hosted `ubuntu-latest` runner (testcontainers-go's own CI matrix runs unmodified against exactly that runner image). CI needs no `services:` block and no compose file — the command that fails in CI is the literal command a contributor runs locally, because there is only one command. Chosen — see Decision.

### Absent-database policy (question 2)

- **`t.Skip` on a missing `DATABASE_URL`.** Rejected outright — this is the shape CLAUDE.md's fail-closed rule already names by its consequence: a green suite that ran nothing.
- **`t.Fatal`/hard failure on every `go test ./...` invocation, unconditionally.** Technically fail-closed, but it makes Docker a prerequisite for the `internal/rules` fast loop too, since `go test ./...` compiles and runs every package in one invocation. This is the cost CONTRIBUTING.md's Requirements section already promises the project will not impose.
- **A build tag (`//go:build integration`) separating these files from the default build, paired with a hard failure — never a skip — inside whichever command *does* compile them.** `go test ./...` without the tag does not merely skip these tests, it never compiles the files that contain them — there is no code path inside that invocation that could be mistaken for having run and passed. A **separate**, explicitly named command owns the tag, and *that* command fails hard, unconditionally, the moment Docker is unreachable. Chosen — see Decision.

### Placement relative to `make check` (question 3)

- **Fold into `check`/`check-nosecrets`'s aggregate.** Rejected: this reintroduces exactly the cost CONTRIBUTING.md's Requirements section rules out, and for every contributor and every doc-only CI run, not only ones touching `internal/store`.
- **Leave it a fully manual target, uninvoked by CI at all.** Rejected: an integration suite nobody's CI runs is the "we'd notice" failure mode the issue itself already calls out as unacceptable — a real regression in the persistence layer would only surface when a human happens to run it.
- **A separate, required CI job — the same shape `replay` and `bench-compare` already are.** `replay`'s cross-OS matrix is already "required, but not folded into `check`'s own aggregate line," for cost reasons stated inline in the Makefile; `bench-compare` is already "required when it runs, but path-gated to skip on most pull requests." The Postgres-backed layer combines both properties: expensive to run everywhere, but non-vacuous and required whenever the code paths it covers change. Chosen — see Decision.

## Decision

**Mechanism: testcontainers-go, pinned to an exact Postgres 16 manifest digest recorded as a Go constant**, never a floating tag. A new, non-production test-support package, `internal/store/storetest`, owns it — a normal Go package (not itself `_test.go`), imported only from other packages' `_test.go` files, so it never reaches `cmd/server` or `cmd/replay`'s production build regardless of what `go.mod` lists as a dependency. **Any `internal/store` test file that imports `storetest` must be an external test, `package store_test`, never the internal `package store`.** `storetest` imports `internal/store` for `Migrate()`; Go rejects the resulting `store → storetest → store` cycle when a test file shares its package's own name, precisely because that combined build target would need `storetest` before `storetest`'s own dependency on plain `store` could resolve. The external-test convention exists exactly to break this, costs nothing here since these tests already exercise `internal/store`'s public API, and is the same discipline the standard library's own `httptest`-style helper packages rely on.

**Container lifecycle is lazy, and per package.** `storetest.Container(t *testing.T)` starts the container the first time any test in that package's binary calls it (`sync.Once`, keyed per test binary — which is per package, since that's the unit `go test ./...` already runs as a separate process), migrates it exactly once via **the real production `store.Migrate()` function** (RFC §7.5's `goose.Up` against the embedded `embed.FS`, advisory lock included — not a dumped/faked schema), and reuses that single migrated instance for every test in the package. **Startup happens inside a test body, never inside `TestMain`.** This is deliberate: `go test -list` executes `TestMain` (if one exists) but never any individual test body, so a `TestMain`-triggered container start would make even `-list` require Docker — exactly the coupling being designed against. Lazy, per-test-body startup keeps `-list` genuinely free of any Docker dependency, which is what the fail-closed guard below relies on.

**The startup error is captured, not raised, inside the `sync.Once`.** `Once.Do`'s completion marks itself done via a deferred store, so it fires even when its function calls `runtime.Goexit` — which is exactly what `t.Fatal` does — meaning a `t.Fatal` called *inside* the guarded closure would let `Once` report "done" after a failed start, and every later test in the package would sail past a container that never came up. `Container` instead assigns the start error to a package-level variable from inside `Do`, and calls `t.Fatal` on that stored error *after* `Do` returns — on every call, first or hundredth — so a failed first attempt fails every subsequent test in the package the same way, rather than only the first one loudly and everything after it silently.

**Migration targets an idle template that no ordinary test ever queries, so cloning it never races an open connection.** `Migrate()` runs once into a template database nothing but `storetest`'s own setup ever connects to; tier 1 below runs against a separate **working** database (`CREATE DATABASE work TEMPLATE <the idle template>`, cloned once per package alongside it) that ordinary tests actually open transactions against. Postgres refuses `CREATE DATABASE ... TEMPLATE` while any other session holds a connection to the source (a documented restriction, not a performance note), so tiers 2 and 3 below clone from the untouched idle template — never from `work` — and are correct regardless of how many transactions tier 1 currently has open.

**Isolation is three-tiered, matching the shape of what each layer actually needs:**

1. **Ordinary Integration-layer tests** (§16.1: "full match through the HTTP layer") run inside a transaction opened against the `work` database at test start and rolled back in `t.Cleanup` — one connection, no commit ever visible outside the test. `sqlc`-generated `Queries` already accept any `DBTX`-shaped value (RFC §7.5), and `pgx.Tx` satisfies that interface, so the test-side store is handed a transaction instead of the pool with no change to production code. **M3 itself has no HTTP layer to route that transaction through** — `internal/web` and `cmd/server` stay `doc.go`/an empty `main` until M5 (RFC §21) — so M3's own Integration-layer tests exercise `internal/store` and `internal/match` directly, one level below the HTTP surface §16.1's row describes in full. Threading a `pgx.Tx`-scoped store through `internal/web`'s eventual handler construction, so a live request sees the same uncommitted fixtures, is M5's own decision once that layer's shape exists — the same kind of deferral D45 already made for its live dashboard page, and for the same reason: designing a server injection seam for a package that is still `doc.go` would be guessing at an architecture this decision has no basis to fix.
2. **The `SELECT … FOR UPDATE` contention test**, which genuinely needs two live connections and real commits, gets `storetest.FreshDatabase(t)`: `CREATE DATABASE test_<random> TEMPLATE <the idle template>` against the same running container. Postgres's template-copy is a file-level clone, not a re-run of every migration, so this is cheap even paid once per test. Real, independent connections; real commits. **Cleanup order matters**: `t.Cleanup` closes every connection `FreshDatabase` itself opened first, then issues `DROP DATABASE ... WITH (FORCE)` from a separate connection to the idle template (never to the database being dropped — Postgres refuses `DROP DATABASE` on the database a session is connected to, the same restriction `CREATE DATABASE ... TEMPLATE` has on its source). `WITH (FORCE)` (Postgres 13+) is used deliberately rather than tracking every connection the test might have opened by hand — a test that fails partway through and leaks a connection must not also fail its own cleanup and obscure the real failure behind a `DROP DATABASE` error.
3. **The migration-race exit demonstration** (explicitly out of scope for this decision, per the issue's own note, but this decision supplies its database) gets `storetest.FreshUnmigratedDatabase(t)` — `CREATE DATABASE ... TEMPLATE template0`, deliberately *not* the idle template, so two processes can race `Migrate()`'s own advisory lock against a database that has genuinely never seen it. This is a different fixture from tier 2 answering a different question — tier 2 needs an already-migrated schema to contend on, tier 3 needs the absence of one — and the two are never interchangeable. **This decision's job stops at handing back that database's connection string**; `FreshUnmigratedDatabase` returns one, provisioned from a single call. Orchestrating the two real OS processes the exit demo needs — starting both, passing each the same connection string as an argument or environment variable, and asserting both come up with migrations applied exactly once — is ordinary process orchestration for that exit demonstration's own harness to build, not a database-provisioning question this decision needs to answer, and not one `*testing.T` (scoped to a single process) could express directly regardless.

**Migrations run the real path, not a faster substitute.** RFC §7.5's `Migrate()` is called directly by `storetest`'s setup, unmodified — the same advisory-lock code every production boot runs. A dumped-schema shortcut was rejected because it would leave the actual migration path — and by extension a real regression in a migration file — completely unexercised by anything in the test suite except the one out-of-scope exit demo. The one-time-per-package cost is paid once, not once per test, by templating from the migrated instance rather than re-running `goose` per test.

**Absent-database policy: build tag, and a hard failure inside the tagged command, never a skip.** Every file for both layers carries `//go:build integration`. `go test ./...` (and therefore `make test`, and `make check`) never compiles these files — there is no code path inside that invocation to mistake for "ran and passed." A new Makefile target, `make integration`, runs `go test -tags integration -race ./...`; inside it, `storetest.Container` calling testcontainers-go with an unreachable Docker daemon returns an error that the helper turns into `t.Fatal`, not `t.Skip` — there is no `DATABASE_URL`-shaped escape hatch anywhere in this design for a Postgres-backed test to quietly not run.

**[Corrected by D54]** [D54](D54-integration-tag-fog-gate-and-check-scope.md) moves `integration-list` out of `check-nosecrets`'s aggregate too — see its own required CI job, described in the paragraph below and corrected inline there. Nothing about `integration` itself, or about the rest of this placement, changes.

**Placement: `make integration` stays out of `check`'s aggregate, in its own required CI job, path-gated the same way `check` and `replay` already are** — reusing the identical broad path list those two jobs already share (the whole `internal` and `cmd` trees, plus `go.mod`, `go.sum`, `Makefile`, and this job's own workflow/action definitions) rather than a narrower, hand-maintained enumeration. The integration suite's real dependency graph already spans `internal/rules`, `internal/game`, `internal/match` and `internal/store`, and will grow to include `internal/web`/`cmd/server` once M5 builds the HTTP layer §16.1's Integration row describes; reusing `check`/`replay`'s existing list means that growth needs no matching edit here, where a bespoke list would silently go stale the first time a new package joined the dependency graph. The Makefile's comment block above `check-nosecrets` gains a paragraph in the same voice as its existing `generate-check`/`bench-compare` entries, naming `integration` and stating this exact reasoning inline — not a fourth unexplained exception.

**Fail-closed guard on the guard.** A new, Docker-free target, `make integration-list`, runs `go test -tags integration -list '^Test(Integration|Concurrency)'` scoped only to the packages allowed to hold `//go:build integration` files (`internal/store`, `internal/match`, `cmd/replay`, `storetest` itself) — never a bare `-list '.*' ./...` across the whole module. Every Integration- and Concurrency-layer test function is named `TestIntegrationXxx`/`TestConcurrencyXxx`, a naming convention this decision fixes for that reason: a floor check over `./...` would count every ordinary test in the repository too, and losing every integration test to a mistyped build tag would vanish inside a total dominated by hundreds of unrelated names, exactly the sort of dilution that makes a floor meaningless. Scoping by package *and* filtering by name means the only names `-list` can return here are the ones this layer owns, so losing one is directly visible as a smaller number against the floor. This compiles every tagged file (an excluded file contributes zero names to the count) without executing any test body, hence without touching Docker at all. `scripts/check-integration-coverage.sh` wraps it and fails if the returned test-name count drops below a floor recorded in the script, bumped upward only, the same discipline `check-bench-regression.sh` and the bots-isolation allow-list already hold contributors to. Needing no Docker was the criterion this document used to decide the check should run everywhere. **[Corrected by D54]** [D54](D54-integration-tag-fog-gate-and-check-scope.md) found that criterion necessary but not sufficient: compiling `storetest`'s import of testcontainers-go still costs a first-time module download and a heavier build than anything else on `check-nosecrets`'s line, so `integration-list` instead gets its own required, always-run CI job, kept out of `check`'s aggregate the same way `generate-check`/`bench-compare` already are — not folded into `check-nosecrets`. It is still the piece that actually catches "the integration suite silently shrank to nothing," the failure mode CLAUDE.md's fail-closed rule exists to prevent; it is simply no longer the local `make check` invocation that proves it on every run.

## Reasoning

**testcontainers-go resolves the mechanism and the determinism concern together, rather than requiring a second policy on top of the mechanism.** A CI service container and a local `docker compose` file are two descriptions of the same intended database that can drift from each other; testcontainers-go is one description — a pinned image reference in Go source — read by both CI and a laptop through the identical code path. "The same one, every time" (the RFC's own phrasing for why the Concurrency layer's clock test needs a pinned image) falls out of this for free: there is only one place the image reference is written down.

**The build tag is not a skip, and the distinction is not semantic hand-waving.** A `t.Skip` claims to have run the check and reports that it did not apply; a build tag means the excluded file was never part of the artifact the command in question compiled at all, the same way `internal/rules` never having a database dependency isn't `internal/rules` "skipping" a Postgres check — it was never in scope for one. `make check` was never the command that owned these tests; `make integration` is, from the moment it exists, and *that* command fails hard, unconditionally, the instant it runs and can't reach Docker. This is the same shape CONTRIBUTING.md already accepts for `replay` (a required job, kept out of `check`'s own aggregate line, for stated cost reasons) and for `bench-compare` (required when it runs, skipped by a path gate on most PRs) — not a new kind of exception, the same one applied to a third gate.

**The guard-on-the-guard has to be Docker-free and non-skippable in CI, or it doesn't guard anything.** A coverage check that itself needs Docker to run would be exactly as skippable as the thing it's supposed to catch skipping — a second gate with the same failure mode one level up. Compiling under the build tag without executing any test body (`-list`, with container startup deliberately kept out of `TestMain`) is what lets this specific check run on every CI job and, if a contributor chooses to invoke it, every machine, Docker or not, and be the thing that actually makes "the integration suite silently shrank to nothing" detectable rather than merely hoped against. **[Corrected by D54]** This paragraph originally required that non-skippability be enforced by riding inside `check`'s own aggregate — [D54](D54-integration-tag-fog-gate-and-check-scope.md) found a required, always-run CI job enforces the identical guarantee (nothing merges without it passing) without also making it a local `make check` build input.

**The three-tier isolation answers "per test, per package, or one rolled-back transaction" by recognizing those aren't competing answers to one question — they're the right answer to three different questions the issue bundled together.** An ordinary Integration-layer test asserting one match's behavior through the HTTP layer needs isolation from every other test, not visibility across connections — a rolled-back transaction is the cheapest thing that provides exactly that, and sqlc's existing `DBTX` abstraction (RFC §7.5) makes it free to wire in. The `FOR UPDATE` contention test and the migration race are each asserting something *about* cross-connection visibility itself — wrapping either in an enclosing transaction would make the property under test (two independent connections actually contending) impossible to construct, since Postgres transactions don't nest. Both need the heavier `CREATE DATABASE ... TEMPLATE` step instead of a rolled-back transaction, but not the *same* template: the contention test needs a schema already there to contend over, so it clones the idle migrated template; the migration race needs the absence of one, so it clones `template0` and never touches the migrated template at all. Cloning either is still cheap enough to pay per test rather than per package, since Postgres's template-copy is a file-level operation, not a re-run of migrations or a rebuild from scratch.

## Consequences

- New package `internal/store/storetest`: `Container(t)` (lazy, per-package, real `Migrate()` into an idle template plus a cloned `work` database), `FreshDatabase(t)` (clone of the idle template, real commits, the `FOR UPDATE` contention test only), `FreshUnmigratedDatabase(t)` (for the migration-race exit demo, out of scope here). Test-only in practice; needs an entry in `scripts/packages.txt` in the implementing PR, mechanically, the same way D34's `internal/telemetry` addition landed with its own PR rather than this decision. Any `internal/store` test file importing it must be `package store_test`, not `package store`, to avoid the import cycle Go's tooling rejects.
- `internal/store`'s production code needs no new abstraction to support transaction-scoped tests — sqlc's existing `DBTX` interface already accepts `pgx.Tx` in place of the pool.
- Every Integration- and Concurrency-layer test file carries `//go:build integration`, and every test function inside them is named `TestIntegrationXxx`/`TestConcurrencyXxx`; none of them exist inside `go test ./...`'s default compilation, so `make test`/`make check` are unaffected by this decision's Docker dependency, unconditionally.
- New Makefile targets: `integration` (Docker-required, `-race`, hard failure on an unreachable daemon — no `t.Skip` path anywhere in this design) and `integration-list` (Docker-free, package-and-name-scoped `-list`). **[Corrected by D54]** Neither joins `check-nosecrets`'s aggregate — [D54](D54-integration-tag-fog-gate-and-check-scope.md) found `integration-list`'s compile cost (a first-time testcontainers-go module fetch) too heavy for the default `make check` loop despite needing no Docker, and gave it its own required CI job instead, described below. `require-docker` joins the existing `require-%` tool-presence pattern.
- New `scripts/check-integration-coverage.sh`, wrapping `integration-list`'s scoped output against a floor count, bumped upward only as tests are added — the mechanism that actually catches a silently-shrunk suite, matching `check-bench-regression.sh`'s and the bots-isolation allow-list's existing discipline.
- CI gains one new required job, `integration`, path-gated via `.github/actions/changed-paths` reusing `check`/`replay`'s existing broad path list (not a bespoke, narrower one) — same fail-open-on-unresolvable-diff posture those jobs already share. No `services:` block; the job's only setup is the Go toolchain, identical to every other job here. **[Corrected by D54]** `integration-list`'s coverage check no longer rides inside the `check`/`check-nosecrets` job; it gets its own required CI job, path-gated the same way, so it runs without becoming a local `make check` build input.
- The Makefile's comment block above `check-nosecrets` gains one paragraph, in the voice of its existing `generate-check`/`bench-compare` entries, naming `integration` and pointing here for the reasoning.
- Reversible at moderate cost before `internal/store` is built: this is a documents-and-tooling decision with no game-state or fixture consequence. After M3's integration suite exists against this shape, switching mechanisms would mean rewriting every test's setup call, but nothing here touches `Resolve`, golden replays, or any fixture — the blast radius stops at `internal/store`'s own test files and this repo's CI/Makefile definitions.
