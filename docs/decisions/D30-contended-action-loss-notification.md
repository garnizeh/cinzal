# D30 — What does a player see when a contended action loses the race?

**Status:** decided
**Blocks:** [#79](https://github.com/garnizeh/cinzal/issues/79) (property invariants), [#84](https://github.com/garnizeh/cinzal/issues/84) (full match exit demo)
**Decided:** 2026-08-16
**Issue:** [#153](https://github.com/garnizeh/cinzal/issues/153)

## The question

GDD §15.0 ends its Step 0 degradation paragraph with an unqualified promise: *"Orders never silently fail."* `internal/rules` has five paths that currently fail with no event at all — `resolveDeal` (`actions.go:214`), `resolvePickup` (`actions.go:123`), `resolveStakePost`'s post-cap branch (`actions.go:169`), `resolveLedger` (`addons.go:34`), and Open Doors (`incidents.go:463`). Each cites D14's Open Doors ruling as precedent. Is that generalisation correct, and what does §15.0's sentence actually cover?

## Why it is open

D14 §4's ruling is explicit about *why* Open Doors degrades silently: its trigger is unknowable at submission, so *"every failure mode here is a resolution-time fact, not one knowable when the order is built."* That reasoning is about a pre-declared boon that may legitimately never fire — it says nothing about a player who declared a valid Deal, walked to the market, and lost a fairness-order race by one position.

`resolveStakePost` makes the inconsistency concrete inside one function: a target already taken returns `EventStakeTargetTaken`, an event; the post cap being reached at resolution returns `nil`, silence — and the function's own doc comment attributes only the second half to D14, even though both are "a legal declaration whose target moved under it."

The event vocabulary already leans away from silence. `game.EventKind` carries four dedicated Step 0 degradation kinds (`EventOrderRejected`, `EventRouteTruncated`, `EventStakeTargetTaken`, `EventPickupTargetGone`, `EventCurfewTruncated`, `EventDeliveryBlocked` — six, not four; the doc comment introducing them undercounts its own list), every one created so a player learns *specifically* why an order didn't do what they asked. Their own doc comment in `event.go` already states the fog reasoning that matters here: *"None of the four is in RFC §9.1's authorised-writer table: they are producer-side bookkeeping for the acting seat's own order, not a fact about another seat's position, so no fog question arises for them."* That reasoning was written for Step 0. Nothing about it is Step-0-specific — it holds identically for a failure discovered at Step N+1 or N+3, because what makes it fog-safe is that the event names only the acting seat, about a node they already know they were at, never a rival.

RFC §11.3 renders resolution as a narrated list built from the event stream. Under today's behaviour, a player who walked three steps to buy a Shiv and lost the race gets no line in that narration at all — indistinguishable, from inside the fog, from having mis-plotted the route. RFC §6.6 names this exact failure shape for implementers — *"a rule simply stops firing, and nobody notices, because the absence of a trail entry looks exactly like nothing having happened"* — and it applies with equal force to the player reading their own recap.

Textually, §15.0's sentence sits inside the paragraph introducing Step 0 specifically ("The target node got staked by someone else... the route truncates... The player is notified with the specific reason. Orders never silently fail."). Read narrowly, that scopes the promise to pre-movement degradation only, leaving Step N+1 (Actions) and Step N+3 (Add-ons) unaddressed by the sentence as written.

## Options

**A — The promise is Step-0-scoped; every later silent path stays silent.** Defensible on placement alone: the sentence sits inside the Step 0 paragraph and nowhere else repeats it. Costs: it does nothing to resolve the `resolveStakePost` split (both branches are Step N+1, so a narrow reading leaves the inconsistency exactly where it started), and it treats a legally-submitted Deal or Pickup as less deserving of a specific reason than a legally-submitted route step — a distinction the GDD gives no rule to justify.

**B — Every path where a legal order's target moved out from under it before resolution emits a private, actor-scoped event, regardless of which step discovers it.** Extends the reasoning `event.go` already states for the four Step 0 kinds — no fog review needed because the event names only the acting seat, about a node they already know they were at — to Step N+1 and Step N+3. Costs: one or more new `EventKind` values.

**C — Reuse the existing Step 0 kinds at resolution time instead of minting new ones.** The precedent partly exists already: `resolveStakePost` reuses `EventStakeTargetTaken` for its target-taken branch, "the same meaning as Step 0's own degradation event, just detected at Step N+1 instead." Costs: `EventPickupTargetGone` is already wired to a distinct Step 0 meaning in `validate.go` (a declared Pickup whose target was never real, checked before movement) — overloading it with resolvePickup's Step N+1 race-loss would conflate two different specific reasons under one kind, exactly the ambiguity the six existing kinds were split apart to avoid (`EventRouteTruncated` vs. `EventCurfewTruncated` cover the same effect for two different, separately-named causes).

Open Doors is not a fourth option here — it is out of scope for either resolution. It is not a declared Action; it is a conditional add-on whose trigger is unknowable at submission (D14 §4), so its non-firing is not a failure of a chosen action, the same way a Bolt Hole that never fires because no confrontation happened isn't one. D14's ruling for it stands untouched.

## Decision

**Option B**, for the four paths that are genuinely "a legal order's target moved before it resolved": `resolveDeal`'s two branches, `resolvePickup`'s two branches, `resolveStakePost`'s post-cap branch, and `resolveLedger`. Each gets a dedicated, private, actor-scoped `EventKind`, following the shape the six existing Step 0 kinds already establish, and reported to no one but the acting seat.

**GDD §15.0's promise generalises rather than staying Step-0-scoped.** *"Orders never silently fail"* is read as the resolution pipeline's standing guarantee, not a sentence bound to the paragraph it happens to sit in: wherever a legally-submitted order's declared action fails to do what it said — whether the world moved under it before movement (Step 0), during Actions (Step N+1), or during Add-ons (Step N+3) — the player gets a specific reason. The one carve-out is Open Doors, and it survives for the reason D14 already gave: a pre-declared, conditionally-triggered boon that may never fire at all is not the same category of thing as a declared action that fails.

**One kind per distinct cause, not one kind per silent `nil`.** Matching the six existing kinds' own granularity (`EventRouteTruncated` and `EventCurfewTruncated` are the same *effect* — a truncated route — kept as separate kinds because the *cause* differs and each is its own "specific reason"):

- `resolveDeal`: the item raced away (an earlier seat's own Deal already bought it this round) is a different specific reason from the seat's own balance no longer covering the price — two kinds.
- `resolvePickup`: the seat's cargo slot already being full is a different specific reason from neither the ground crate nor the Warehouse contract being there to take — two kinds.
- `resolveStakePost`: the post-cap branch gets its own new kind, landing beside the existing `EventStakeTargetTaken` rather than merging into it — the two causes ("someone else already holds this exact node" vs. "you're already at your own cap") are not the same reason even though both currently sit in the same function.
- `resolveLedger`: one kind, the balance no longer covering `LedgerCost` — there is only one cause here, so no split is needed.

That is six new `EventKind` values, plus the untouched `EventStakeTargetTaken`. This is not Option C: none of the six is folded into an existing kind's meaning, so `EventPickupTargetGone`'s existing Step 0 semantics in `validate.go` stay exactly as documented, and telemetry can always tell a Step 0 failure from a Step N+1 or N+3 one by kind alone.

**Each new kind is exempt from RFC §9.1's writer table for the same reason the six existing Step 0 kinds are.** It names only the acting seat, about a node or fact they already knew at declaration time, and discloses nothing about any other player's position. `Project` must route every one of them into the acting seat's own resolution feed only — never into `Trail` or `Anchors`, the two surfaces `writeAnchors` (RFC §9.1) actually governs — mirroring exactly how the six existing Step 0 kinds are scoped.

## Reasoning

**The fog argument that already justified the six Step 0 kinds does not know which pipeline step produced them.** It rests on two facts about the event: who it names, and what it discloses to that name. Both facts are identical whether the failure is caught before movement or three steps later during Actions. A framing that treats "Step 0" as the load-bearing category, rather than "actor-scoped, no position disclosed," would have to explain why an event that is fog-safe at Step 0 stops being fog-safe at Step N+1 — and nothing in the RFC's fog model gives that explanation, because nothing about the fog boundary changes between those two steps. The category that actually matters is the one `event.go`'s own comment already names; this decision just stops treating it as coincidentally true of only the first four kinds.

**Treating `resolveStakePost`'s two branches identically was the constraint that ruled out Option A.** Once one branch of a single function already emits an event under the "legal order, world moved" reasoning, defending silence for the other branch under the same reasoning requires a distinction the GDD doesn't draw. The cleanest way to make both branches consistent, without deleting the trace `EventStakeTargetTaken` already provides, is to extend the same treatment to the other branch — which is Option B, not a retreat to Option A.

**Rejecting Option C rests on the six kinds' own history, not a new principle.** `EventRouteTruncated` and `EventCurfewTruncated` already demonstrate that this codebase splits kinds by cause, not by outward shape, whenever the causes are genuinely different reasons a player would want named separately. Reusing `EventPickupTargetGone` for a Step N+1 race loss would be the first time two meaningfully different causes shared one kind, and it would do so at exactly the moment the codebase's telemetry needs to distinguish "your order was invalid before movement even started" from "you moved correctly and still lost a fair race" — two very different signals for balance analysis (#84) and for a player deciding whether to replot their route next time.

**Open Doors stays exactly as D14 left it.** D30 doesn't reopen D14 §4; it answers the question D14 explicitly didn't ask. A pre-declared conditional boon and a declared action are different things, and only the latter is what §15.0's promise was ever describing — an order the player actually submitted, expecting it to do something specific.

## Consequences

- **`internal/game/event.go` gains six new `EventKind` values** — one for `resolveDeal`'s item-gone case, one for `resolveDeal`'s balance case, one for `resolvePickup`'s slot-full case, one for `resolvePickup`'s race-loss case, one for `resolveStakePost`'s post-cap case, one for `resolveLedger`'s balance case (its own kind, not a reuse of `resolveDeal`'s balance kind, since the two fire from different actions and RFC §11.3's recap needs to tell them apart) — each documented the same way the six existing Step 0 kinds are, including an explicit note that it is intentionally absent from RFC §9.1's writer table.
- **`resolveDeal`, `resolvePickup`, `resolveStakePost`, and `resolveLedger` (`internal/rules/actions.go`, `addons.go`) each start returning an event on their currently-`nil` branches.** `resolveLedger` currently returns nothing at all (`func resolveLedger(...)`, no return value) and needs a return type change to carry its new event back to `resolveAddons`, the same shape `resolveRenewal` already has in the same function. This is a task, landed separately from this decision, matching how D11's `Config.Suppress` behaviours and D28's `blockedBordersThisRound` each landed after their own decisions.
- **RFC §9.1 gains one sentence** stating the general exemption this decision formalises: a producer-side event that names only the acting seat, about a fact they already knew when they declared the order, needs no row in the sixteen-row table, because it discloses no other seat's position. This documents in the RFC what has, until now, only ever lived in `event.go`'s code comment.
- **GDD §15.0 gains a clause** stating the promise applies at every resolution step, not only Step 0, with Open Doors named as the one standing exception and why.
- **RFC §11.3's narrated resolution list needs no structural change** — it already renders "what happened to you" from the event stream; it simply now has events to render for six cases that previously produced nothing. Whether the recap phrases these as a distinct visual category from Step 0 degradations is an RFC-002/implementation question, not one this decision needs to settle.
- **No RNG accounting changes.** None of the six new kinds is a draw; each fires off state the resolution pipeline already computed (market stock, cargo state, post ownership, balance) to decide the branch was reached at all.
- Reversible at low cost while `Resolve` is still being built out: none of the six is stored schema, and every one is producer-side bookkeeping. Reverting to silence for any one of them is a one-branch code change plus removing its `EventKind`, not a wire-format change.
